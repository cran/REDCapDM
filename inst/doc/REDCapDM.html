1 Introduction

The REDCapDM package provides a comprehensive toolkit for managing data exported from REDCap. It supports both importing REDCap data (from files or via API), transforming and cleaning the data according to the project’s dictionary and logic, and generating query reports for data validation. In particular, REDCapDM can identify missing or out-of-range values and track changes in identified queries across data versions.



2 Functions

All main functions are listed below (and described in detail in the examples):

2.1 Import data

  • redcap_data(): Read REDCap data into R.

2.2 Explore data

  • rd_missplot(): Plot the missing values per variable and event, or record by record.

2.3 Process data

  • rd_dates(): Standardize date and datetime fields.

  • rd_delete_vars(): Remove specified variables (by name, pattern or form).

  • rd_recalculate(): Recompute calculated fields and compare with REDCap values.

  • rd_factor(): Replace numeric multiple-choice columns with their factor version.

  • rd_checkbox(): Expand checkbox responses with custom labels and rename var___1 columns (REDCap style) to var_option.

  • rd_split(): Split dataset by form or event.

  • rd_insert_na(): Manually set specified variables to missing based on a logical filter.

  • rd_rlogic(): Translate REDCap branching or calculation logic into R syntax.

  • rd_dictionary(): Update dictionary (translation of REDCap logic into R syntax) to reflect transformed data and logic.

Or we can use these functions at once, except rd_insert_na() (its filters are specific to each project, so it is applied separately):

  • rd_transform(): One-step pipeline to clean and preprocess the raw REDCap data.

2.4 Queries

  • rd_query(): Apply expressions to identify data queries/issues.

  • rd_event(): Report the events that are missing in each record (longitudinal): whether the event is present, not whether it is complete.

  • check_queries(): Compare two query reports to track changes made.

  • rd_export(): Export query/report tables to an Excel (.xlsx) file.

Each group of functions is explained in detail in its own vignette: vignette("missing-data"), vignette("data-processing") and vignette("query-management").



3 Installation

The release version can be installed from CRAN:

install.packages("REDCapDM")

The development version can be installed from GitHub:

install.packages("remotes") # Run this line if the 'remotes' package isn't installed already.
remotes::install_github("bruigtp/REDCapDM")

5 Usage

The package structure can be divided into three main components: reading raw data, processing data and identifying queries. Typically, after collecting data in REDCap, we will have to follow these three components in order to have a final validated dataset for analysis. We will provide a complete basic user guide on how to perform each one of these steps using the package’s functions. For the processing of the data and query identification, we will use the covican built-in dataset as an example.

5.1 Read data

5.1.1 redcap_data

The redcap_data() function allows users to easily import data from a REDCap project into R.

In order to read exported data, please select R Statistical Software in REDCap and download both the generated R script and its associated CSV data. The dictionary can be downloaded separately in CSV or XLSX format. Then use the arguments data_path and dic_path to designate the local path where we have stored the R file and the dictionary from the REDCap project:

dataset <- redcap_data(data_path = "C:/Users/username/example.r",
                       dic_path = "C:/Users/username/example_dictionary.csv")

Note: The R and data CSV file exported from REDCap must be located in the same directory.

If the REDCap project is longitudinal (its data has the column redcap_event_name, also when the export has a single event) then a third element should be specified with the correspondence of each event with each form of the project. This csv file can be downloaded in the REDCap of the project following these steps: Project Setup < Designate Instruments for My Events < Download instrument-event mappings (CSV). Then, it has to be specified using the argument event_path:

dataset <- redcap_data(data_path = "C:/Users/username/example.r",
                       dic_path = "C:/Users/username/example_dictionary.csv",
                       event_path = "C:/Users/username/events.csv")

Note: if the project is longitudinal and the event-form file is not provided using the event_path argument, some steps of the processing can not be performed.

Another way to read data exported from a REDCap project is using an API connection. To do this, we can use the arguments uri and token which respectively refer to the uniform resource identifier of the REDCap project and the user-specific string that serves as the password:

dataset_api <- redcap_data(uri = "https://redcap.example.org/api/",
                           token = Sys.getenv("REDCAP_TOKEN"))

In this case, there is no need to specify the event-form file since the function will download it automatically using the API connection, if the project is longitudinal.

With the API, redcap_data() makes several requests: the metadata of the project (dictionary, events, instruments, …) and the records, whose values and labels are read separately (in batches of records, and the labels again if the records changed). The record identifiers are kept as text while they are read, so long identifiers (e.g. 9007199254740993, beyond the precision of the numbers of R) or identifiers with zeros on the left (e.g. 007) are not changed; as with the exported files, the identifier is a number only when its text is that number. The labels of the events, repeated instruments and Data Access Groups (the .factor columns) are given to each row by its code, such as the unique event name, and they are checked with the metadata of the project: if someone changes the records while they are read, the labels are read again, and the function stops with an error if they keep changing.

Warning: Please keep in mind that the API token gives you special access to the REDCap project and that it should not be shared with other people. Instead of writing it in your scripts, save it in your .Renviron file (e.g. with usethis::edit_r_environ(), adding a line REDCAP_TOKEN=...) and read it with Sys.getenv("REDCAP_TOKEN"), as in the example above.

The redcap_data() function returns a list with the imported data and the dictionary, and also the event-form mapping in longitudinal projects when it is available (given in event_path, or read from the API).

If the project uses REDCap’s Missing Data Codes (e.g. NI, UNK, ASKU), by default (rm_mdc = TRUE) they are replaced by missing values (NA), with a warning when the data has them and the codes of the project weren’t given in mdc. With rm_mdc = FALSE, they are kept in a new <field>_mdc column next to the field, with the original code of each row: in the validated text fields (numbers, dates, …), the field keeps its type and has NA in those rows, and the multiple-choice variables also have the code as an additional category of their .factor version. Use the _mdc column to know which code each row had. A warning lists the validated text fields with codes, only when the data has them (the codes of the multiple-choice variables are kept without a warning):

dataset <- redcap_data(data_path = "C:/Users/username/example.r",
                       dic_path = "C:/Users/username/example_dictionary.csv",
                       rm_mdc = FALSE)

If the project has its own Missing Data Codes, give them in the mdc argument, optionally with their labels (with the API, the codes defined in the project are read automatically). They are handled like the default codes of REDCap, which are always used:

dataset <- redcap_data(data_path = "C:/Users/username/example.r",
                       dic_path = "C:/Users/username/example_dictionary.csv",
                       mdc = c("-999" = "Not applicable", "-888" = "Unknown"))

The rd_missplot() function plots the missing values of the dataset, per variable and event or record by record. See vignette("missing-data").


5.3 Process

Given any data imported from REDCap with redcap_data(), this would be the pipeline of an entire processing workflow:

dataset |> 
    rd_delete_vars(pattern = c("_complete", "_timestamp")) |>
    rd_dates() |>
    rd_recalculate() |> 
    rd_checkbox() |> 
    rd_factor() |> 
    rd_dictionary() |> 
    rd_split(by = "event") # use "form" if not longitudinal

All functions are optional and should only be used at the user’s discretion when necessary. The order of some functions can also be exchanged. For example, for covican there are no variables to delete and dates are already processed, so the pipeline would be simplified:

covican_transformed <- covican |> 
    rd_recalculate() |> 
    rd_checkbox() |> 
    rd_factor() |> 
    rd_dictionary() |> 
    rd_split(by = "event")

Each of these functions, and rd_transform(), which does all the steps at once, is explained in detail in vignette("data-processing").


5.4 Queries

Queries are very important to ensure the accuracy and reliability of a REDCap dataset. The collected data may contain missing values, inconsistencies, or other potential errors that need to be identified in order to correct them later.

The functions to identify queries, check missing events, follow up the corrections and export the reports are explained in detail in vignette("query-management").
