The examples use covican, the dataset included in the package (described in vignette("REDCapDM")).

For a project assembled from separate data frames, keep the record identifier as the first field of the dictionary, even if its column is moved in the dataset. The processing functions use that field when the identifier is not named record_id.

Given any data imported from REDCap with redcap_data(), this would be the pipeline of an entire processing workflow:

dataset |> 
    rd_delete_vars(pattern = c("_complete", "_timestamp")) |>
    rd_dates() |>
    rd_recalculate() |> 
    rd_checkbox() |> 
    rd_factor() |> 
    rd_dictionary() |> 
    rd_split(by = "event") # use "form" if not longitudinal

All functions are optional and should only be used at the user’s discretion when necessary. The order of some functions can also be exchanged. All the functions that can be used in each step of a processing workflow are detailed below.

1 rd_delete_vars

This function removes unwanted variables from both a REDCap dataset and its dictionary. This is especially useful for eliminating automatically generated fields such as form completion flags (*_complete) or timestamps (*_timestamp).

You can delete variables by specifying their exact names, by using regular expression patterns or by choosing whole forms:

# Option A: delete by variable name
covican_deleted <- covican |> 
  rd_delete_vars(vars = c("potassium", "leuk_lymph"))

# Option B: delete by regex pattern (here, the inclusion and exclusion criteria)
covican_deleted <- covican |> 
  rd_delete_vars(pattern = c("^inc_", "^exc_"))

# Option C: delete every variable of a form
covican_deleted <- covican |> 
  rd_delete_vars(forms = "laboratory_findings")

When variables are deleted:

  • They are removed from both the dataset and dictionary.

  • Factor versions of deleted variables (if present) are also removed.

  • If a pattern doesn’t match any variable, a warning tells you that nothing was removed. The columns that REDCap uses for the record identifier, the events and the repetitions are never removed by a pattern.

  • With forms, the checkbox options, recalculated versions (_recalc) and the _complete/_timestamp fields of the form are removed too, and the form is removed from the event-form mapping. The record identifier is always kept.


2 rd_dates

This function is designed to process and standardize date and datetime fields in a REDCap dataset. In REDCap projects, date and datetime fields can sometimes be stored as character strings, which can make analyses difficult. This function detects which fields should be dates/datetimes from the REDCap dictionary and converts them to Date and POSIXct, respectively. Datetimes written as text are parsed in UTC, preserving the clock time written in REDCap; existing POSIXct columns keep their time zone.

covican_dates <- covican |> 
  rd_dates()

Quick verification example:

# Simulate a character date since covican already has the dates in the correct format
covican_dates <- covican
covican_dates$data <- covican_dates$data |> 
  dplyr::mutate(d_birth = as.character(d_birth))
# Check class before conversion

class(covican_dates$data$d_birth)
#> [1] "character"

# Check class after conversion
covican_dates <- covican_dates |> 
  rd_dates()
class(covican_dates$data$d_birth)
#> [1] "Date"

After this transformation, all date and datetime variables are standardized and ready for analysis in R.


3 rd_recalculate

This function identifies calculated fields in a REDCap project, translates their calculation logic into R, recalculates the values, and compares the results with the values stored in REDCap.

It then produces a structured report that helps users detect discrepancies between REDCap’s stored calculations and the values recalculated in R.

covican_recalc <- covican |> 
  rd_recalculate()

# Print recalculation results
covican_recalc$results
## Recalculating calculated fields and saving them as '[field_name]_recalc'. (rd_recalculate)
## 
## 
## | Total calculated fields | Non-transcribed fields | Fields with different recalculated values |
## |:-----------------------:|:----------------------:|:-----------------------------------------:|
## |            2            |         0 (0%)         |                  1 (50%)                  |
## 
## 
## |     field_name      | Transcribed? | Is equal? | Different values |
## |:-------------------:|:------------:|:---------:|:----------------:|
## |         age         |     Yes      |   FALSE   |        1         |
## | screening_fail_crit |     Yes      |   TRUE    |        0         |

The results object includes:

  • A summary report outlining the total number of calculated fields, how many were successfully transcribed into R, and how many showed differences between the REDCap values and the recalculated ones.

  • A field-level report listing each calculated field, whether the logic was successfully converted to R, whether the recalculated values match the originals and how many values are different.

You can also exclude specific fields from recalculation (e.g., complex multi-event calculations) to reduce computation time and avoid unnecessary warnings.

# Exclude specific variables from recalculation
covican_recalc <- covican |> 
  rd_recalculate(exclude = "screening_fail_crit")

covican_recalc$results
## Recalculating calculated fields and saving them as '[field_name]_recalc'. (rd_recalculate)
## 
## 
## | Total calculated fields | Non-transcribed fields | Fields with different recalculated values |
## |:-----------------------:|:----------------------:|:-----------------------------------------:|
## |            1            |         0 (0%)         |                 1 (100%)                  |
## 
## 
## | field_name | Transcribed? | Is equal? | Different values |
## |:----------:|:------------:|:---------:|:----------------:|
## |    age     |     Yes      |   FALSE   |        1         |

After running this function:

  • For each calculated field whose recalculated values are different from the values of REDCap, a new variable with the suffix _recalc is added to the dataset, placed immediately after the original variable and containing the recalculated values.

  • The data dictionary is updated with a corresponding entry, where the original variable label is extended with "(Recalculated)" to make these fields easy to identify.

The recalculation gives the same results if the variables used in the calculations have already been converted to factors with rd_factor(). Running the function again on its own output updates the _recalc variables instead of duplicating them.


4 rd_checkbox

This function cleans and restructures REDCap checkbox fields. It converts the default "Unchecked/Checked" categories of checkbox responses created by REDCap into user-specified labels (default "No"/"Yes") and renames the varname___code variables (original REDCap structure) to readable names based on the text of the checkbox options. Additionally, it updates the dictionary to match the new variable names. This includes choices, calculations, and branching logic.

# Default transformation: "No"/"Yes" labels & renamed variables
cb <- covican |> 
  rd_checkbox()

str(cb$data$underlying_disease_hemato_acute_myeloid_leukemia.factor)
##  Factor w/ 2 levels "No","Yes": 1 NA 1 NA 1 NA 1 NA 1 NA ...
##  - attr(*, "label")= chr ""

For example, consider the checkbox field of the type of underlying disease present in the covican dataset. Originally, the variables were named type_underlying_disease___0 and type_underlying_disease___1, while the option labels were ‘Haematological cancer’ and ‘Solid tumour’. After running the function, the variables are renamed to type_underlying_disease_haematological_cancer and type_underlying_disease_solid_tumour, reflecting the option text in a readable format.

To preserve the original REDCap-style names (e.g., varname___1, varname___2) instead of renaming variables based on option text:

# use the argument checkbox_names to choose the final format of the variable names
cb <- covican |> 
  rd_checkbox(checkbox_names = FALSE)

str(cb$data$underlying_disease_hemato___1)
##  num [1:342] 0 NA 0 NA 0 NA 0 NA 0 NA ...
##  - attr(*, "label")= chr "Specify underlying disease (choice=Acute myeloid leukemia)"

In this case, each option becomes a field of the dictionary of its own, so running rd_checkbox() again on the result stops with an error instead of converting them again. As the data of redcap_data() has the .factor versions of the options, the columns keep their codes 0/1 (as above) and their .factor versions take the labels; without the .factor versions, the values of the columns become the labels.

If a checkbox field has a branching logic, the na_logic argument controls how missing values are set, with the following options:

  • "none": do not set NA based on branching logic.

  • "missing" (default): set NA only where the branching logic evaluation is NA.

  • "eval": set NA where the branching logic evaluates to FALSE or NA (i.e., logic not satisfied or missing).

cb <- covican |> 
  rd_checkbox(na_logic = "eval")

By default, checkbox factors are labeled "No" and "Yes", but you can specify alternative labels:

cb <- covican |> 
  rd_checkbox(checkbox_labels = c("Absent", "Present"))

str(cb$data$underlying_disease_hemato_acute_myeloid_leukemia.factor)
##  Factor w/ 2 levels "Absent","Present": 1 NA 1 NA 1 NA 1 NA 1 NA ...
##  - attr(*, "label")= chr ""


5 rd_factor

This function converts categorical variables in a REDCap dataset into R factors by replacing each original variable (numeric version) with its corresponding .factor version created by REDCap. If a .factor column is text instead of a factor (e.g. after modifying the data), it is converted to a factor with the levels in the order of the options of the dictionary.

factored <- covican |> 
  rd_factor()

# Checking class of the variable
str(factored$data$available_analytics)
##  Factor w/ 2 levels "No","Yes": 2 2 2 2 2 1 2 NA 2 1 ...
##  - attr(*, "label")= chr "Blood test available? (+/- 72h)"

If you need to keep certain variables in their raw form, you can list them in the exclude argument. This prevents those variables from being replaced (including their .factor version) while still allowing the rest of the dataset to be converted.

factored <- covican |> 
  rd_factor(exclude = c("available_analytics", "urine_culture"))

# The excluded variables keep both versions
str(factored$data$available_analytics)
##  'labelled' int [1:342] 1 1 1 1 1 0 1 NA 1 0 ...
##  - attr(*, "label")= chr "Blood test available? (+/- 72h)"
str(factored$data$available_analytics.factor)
##  Factor w/ 2 levels "No","Yes": 2 2 2 2 2 1 2 NA 2 1 ...
##  - attr(*, "label")= chr ""

Note: the function automatically excludes these system variables from conversion: redcap_event_name, redcap_repeat_instrument, redcap_data_access_group. These variables are retained as-is to avoid interfering with longitudinal event mappings or user access groups.

After conversion, the converted variables are factors and their .factor versions are removed. The variables in exclude, the system variables above and the variables whose labels are of several codes (e.g. two options with the same label, which rd_factor() reports with a warning) keep both columns.

Note: use rd_factor() before rd_dictionary(). The branching logic and calculations translated to R by rd_dictionary() compare the variables with their original codes, so they stop working once the variables are factors. If rd_factor() detects this situation, it shows a warning.


6 rd_dictionary

When working with REDCap exports, the data dictionary contains field metadata, branching logic, and calculation rules written in REDCap logic. The rd_dictionary() function refreshes branching logic and calculations, translating them from REDCap logic into R logic, and ensures the dictionary remains consistent with the cleaned dataset.

# Update dictionary after cleaning
dict_result <- covican |>
  rd_checkbox() |>
  rd_factor() |>
  rd_dictionary()

When we transform the dictionary:

  • Updates branching logic expressions so they match factor labels rather than numeric codes.

  • Converts calculations and logic into R-friendly expressions.

  • Reports any fields where branching logic or calculations could not be converted.

If repeated entries exist, you can reshape the data into wide format:

forms_data <- covican |>
  rd_split(by = "form", wide = TRUE)

With wide = TRUE, the result also has the column max_repeated_instance: the largest number of rows of a record in each form (its events and repetitions), which is the number of the last set of columns. It is not the number of the instance: the columns are numbered by the position of each row of the record (e.g. a record with the instances 2 and 5 has the columns _1 and _2, and its maximum is 2).

Note: For longitudinal projects, the column events has the events where each form is collected.

Note: the columns of the data must be fields of the dictionary, their .factor and _mdc versions, the options of the checkbox fields or the .factor version of the status of the forms. Any other column stops the function with an error that names it, so that it isn’t left out of the result without notice.

  • By event

For longitudinal projects, you can also split the data by event. The function uses the event_form mapping to assign variables correctly to each event:

8 rd_insert_na

This is an auxiliary function that can be used to set some values of a variable(s) to missing if a certain logic is fulfilled. It can be used, for example, to insert missing values on those checkboxes that do not have a branching logic, as mentioned earlier. For instance, we can transform the checkboxes with the rd_checkbox() function and then use this function to set the values of the checkbox type_underlying_disease_haematological_cancer to missing when the age is less than 65 years old:

cb <- covican |> 
  rd_checkbox()

#Before inserting missing values
table(cb$data$type_underlying_disease_haematological_cancer)

  0   1 
103  87 
#Run with this function
cb2 <- covican |> 
  rd_checkbox() |> 
  rd_insert_na(vars = "type_underlying_disease_haematological_cancer",
               filter = "age < 65")

#After inserting missing values
table(cb2$data$type_underlying_disease_haematological_cancer)

 0  1 
65 50

If the variable has a .factor version, it is also set to missing, so that a later rd_factor() doesn’t bring the values back.

Note that both the variable to be transformed (type_underlying_disease_haematological_cancer) and the variable included in the filter (age) are in the same event. If the variable to be transformed and the filter didn’t have any event in common then the transformation would give an error. Furthermore, if the variable to be transformed was in more events than the filter, only the rows of the events in common would be converted.


9 rd_rlogic

This is also an auxiliary function that transforms the REDCap logic into logic that can be evaluated in R. This function is used internally in multiple functions, for example, rd_dictionary(). It returns a list with:

  • rlogic: the transformed logic. It can use auxiliary columns (e.g. the values of other events of the record) and internal functions of the package, so it can’t always be evaluated directly on the original dataset: use eval or eval_data.

  • eval: the result of the evaluation of the logic in R, one value per row of the dataset, with NA outside the events and rows where the variable is collected. A logic without variables (e.g. 1 + 1) can give a single value in a dataset without events or repetitions.

  • eval_data: a data frame with the record identifier, the event (and repetition, if any) and eval, to identify the record of each evaluated value.

This function doesn’t modify the dataset, so it has to be used outside the transform workflow.

Let’s see how it transforms the logic of one of the calculated fields in the built-in dataset:

logic_trans <- covican |> 
  rd_rlogic(logic = "if([exc_1]='1' or [inc_1]='0' or [inc_2]='0' or [inc_3]='0',1,0)",
            var = "screening_fail_crit")

logic_trans$rlogic
[1] "ifelse(data$exc_1=='1' | data$inc_1=='0' | data$inc_2=='0' | data$inc_3=='0',1,0)"
head(logic_trans$eval_data)
  record_id        redcap_event_name eval
1     100-6     baseline_visit_arm_1    0
2     100-6 follow_up_visit_da_arm_1   NA
3    100-13     baseline_visit_arm_1    0
4    100-13 follow_up_visit_da_arm_1   NA
5    100-16     baseline_visit_arm_1    0
6    100-16 follow_up_visit_da_arm_1   NA

The variables of the logic that have already been converted to factors with rd_factor() are evaluated with their original codes, so the result is the same before and after the conversion.
